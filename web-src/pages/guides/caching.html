Caching and resuming

Every expensive stage stores its output with a key that covers the settings it depends on and the keys of the stages before it. A stage is recomputed only when its key changes.

Stage Main outputs Recomputed when you change
norm norm_s1.parquet, norm_q.parquet --sample, seed
maps token_maps.json Validation share, abbrev_* settings
derive s1.parquet, q.parquet, place_links.json Token maps, filler-word and place settings
finetune embed_model/ Encoder and fine-tuning settings
emb emb.npy Encoder identity, length, dimension
pairs pairs.parquet Any blocking setting, the embeddings, --sim-drop
xtrain X_train.npy Candidates, feature list, sibling settings, training-pair budget
ce ce_model/ Training features, cross-encoder settings
scores (test only) scores.npy Test candidates, or a newly trained model

This has two practical consequences:

  • Interrupted runs resume. Run the same command again, and it continues from the first stage without a valid cache.
  • Experiments are cheap. Changing the number of candidates, for example, re-runs blocking and everything after it, but keeps the normalized records, the fine-tuned encoder and the embeddings.

--force deletes the run's cache folder (work/train/ or work/test/) and starts from scratch. If you change a stage's code in a way that makes old outputs invalid, bump its number in STAGE_VERSION in er/pipeline.py.
