Core concepts

The matching problem

The task: for every Source 1 record, return every Source 2 and Source 3 record of the same business, and nothing else.

Sources S1, S2 and S3

The three sources have different roles:

  • Source 1 (S1) is the reference list. It is deduplicated: each business appears once.
  • Sources 2 and 3 (S2, S3) contain noisy, partial copies of those businesses, plus many records that match nothing. A business can appear several times, in either source.

The training data has 2.2M S1, 5.0M S2 and 5.3M S3 records. Studying it before any modelling showed what the matcher has to handle:

Observation Value What it means for the design
True matches per S1 record mean 3.5 Find whole groups of records, not single pairs.
S1 records with no match 5.6% Returning nothing must be a real option.
Non-Latin names among true matches 7.2% Transliteration, plus embeddings that work across scripts.
Web domains used as names 5.2% Compare names with the spaces removed.
True matches with an empty address 4.4% The name alone must be enough to retrieve a record.
Matches across countries none Country is a hard partition: only same-country records are compared.

One owner per record

In the ground truth, every S2/S3 record belongs to at most one S1 record. There are no exceptions among 7.6M matched records. The pipeline makes this structure explicit and turns the search around: each S2/S3 record is a query, and the S1 records of the same country are the index. Each query picks at most one owner, so two S1 records can never claim the same record.

Distractors

26% of S2/S3 records match no S1 record. These distractors are what makes precision hard. 31% of them share their normalized name with some S1 record, so a matcher that trusts names alone merges them. The files to be matched are even more crowded than the training files: 5.76 S2/S3 records per S1 record, against 4.67 in training (see Simulating a denser crowd).
